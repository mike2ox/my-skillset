`$ARGUMENTS` 맨 앞의 선택적 `--output <파일-경로>`를 먼저 처리하고 제거한 나머지 기능을 계획합니다. 공백이 있는 경로는 인용합니다.

## 출력 경로 옵션

- `--output`은 **파일 경로**만 받습니다. 상대 경로는 현재 프로젝트 디렉터리 기준으로 해석하며, 디렉터리만 넘기면 올바른 파일 경로를 AskUserQuestion으로 다시 받습니다.
- `--output`이 있으면 승인된 plan은 그 정확한 경로에 저장합니다. 상위 디렉터리가 없으면 임의로 만들지 말고, 생성 / 다른 경로 지정 / 저장 취소 중 하나를 AskUserQuestion으로 묻습니다.
- 지정한 파일이 이미 있으면 자동으로 덮어쓰지 말고, 덮어쓰기 / 다른 파일 경로 / 저장 취소 중 하나를 AskUserQuestion으로 묻습니다.
- `--output`이 없을 때는 아래의 기존 `docs/plan/` 기본 저장 규칙과 파일명 규칙을 그대로 적용합니다.

plan 모드를 사용하여 아래 구조로 설계 방향을 정리하고, 승인 후 구현을 시작합니다.

## 0단계: 가정 먼저 드러내기

plan 내용을 쓰기 **전에**, 확인 없이 채워 넣고 있는 가정을 먼저 나열합니다.

```
확인 없이 가정하고 있는 것:
1. 웹 애플리케이션 (네이티브 앱 아님)
2. 인증은 기존 세션 방식 그대로 사용
3. 데이터는 기존 GraphQL 스키마로 충분
→ 다르면 지금 알려주세요. 아니면 이 전제로 진행합니다.
```

모호한 요구사항을 조용히 채워 넣지 않습니다. plan의 존재 이유가 코드를 쓰기 **전에** 오해를 드러내는 것입니다.

요청 자체가 모호하면(대상 사용자·성공 기준·제약 중 하나라도 불명) plan을 쓰지 말고 `/my-interview`를 먼저 권합니다.

## 정리 항목

1. **기능 개요** — 무엇을 만드는지 1-2문장 요약
2. **사용자 스토리** — 누가, 무엇을, 왜 필요한지
3. **성공 기준** — 무엇이 되면 "완료"인지, 가능하면 측정 가능한 형태로
4. **기술적 접근 방향**
   - 관련 파일 및 컴포넌트 구조
   - 필요한 API / GraphQL query·mutation
   - UI 컴포넌트 설계
   - 상태 관리 방식
5. **의존성 순서** — 무엇이 무엇에 의존하는지 (아래 참조)
6. **고려사항** — 엣지 케이스, 성능, 접근성
7. **리스크와 대응** — 아래 표 형식
8. **안 할 것** — 이번 범위에서 명시적으로 제외하는 것
9. **열린 질문** — 사용자 판단이 필요해 아직 못 정한 것

현재 코드베이스의 기존 패턴을 분석하여 일관성을 유지하는 방향으로 제안하세요.

## 의존성 순서 작성법

무엇이 무엇에 의존하는지 그려서, 구현 순서가 자연스럽게 나오게 합니다.

```
스키마 / 타입 정의
    ├── API (query·mutation)
    │       └── 데이터 훅
    │               └── UI 컴포넌트
    └── 검증 로직
```

구현 순서는 이 그래프의 아래(기반)부터 올라갑니다.

## 리스크 표 형식

| 리스크 | 영향도 | 대응 |
|--------|-------|------|
| {불확실한 지점} | 높음/보통/낮음 | {완화 방법 or 먼저 검증할 방법} |

불확실성이 큰 항목은 나중이 아니라 **먼저** 검증하도록 계획합니다. 뒤에서 터지면 그 위에 쌓은 작업이 전부 헛수고가 됩니다.

## 승인 전 자체 점검

plan을 제시하기 전 아래를 확인합니다:

- [ ] 가정을 명시적으로 나열했다
- [ ] 성공 기준이 "동작한다"보다 구체적이다
- [ ] 의존성 순서가 드러나 있다
- [ ] 안 할 것을 적었다
- [ ] 사용자 판단이 필요한 항목을 열린 질문으로 분리했다

## plan 승인 후

`--output`이 있으면 위에서 확정한 파일 경로에 승인된 plan 내용을 저장합니다. 없으면 `docs/plan/YYYY-MM-DD-{기능명}.md` 파일로 저장합니다.
기본 저장일 때만 `docs/plan/` 디렉토리가 없으면 먼저 생성합니다.
저장 완료 후 `/my-split`으로 작업을 분해할 수 있음을 알립니다.
