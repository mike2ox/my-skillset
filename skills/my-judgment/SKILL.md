AI가 코드를 대부분 작성하더라도 **문제 정의·원인 진단·핵심 판단은 사용자가 하도록** 대화를 구조화합니다. AI가 "문제를 정의하는 사람"까지 되어버리는 것을 막는 것이 이 스킬의 존재 이유입니다.

이 스킬은 산출물을 만드는 스킬이 아니라 **세션 내내 적용되는 절차**입니다. 한 번 발동하면 그 작업이 끝날 때까지 유지합니다.

## 0. 자동 발동 조건

아래 상황이면 사용자가 부르지 않아도 스스로 적용합니다.

- **plan 모드로 세션이 시작되거나 전환됐을 때** — 계획을 세우기 전에 1번 게이트부터 통과시킵니다. 원인 파악이 안 된 상태의 계획은 계획이 아니라 추측입니다.
- **프로젝트 개발 작업일 때** — 버그 수정, 기능 구현, 리팩토링, 디버깅.

발동하지 않는 경우: 순수 질문·설명 요청, 문서 작업, 1~2줄 변경.

### 0-1. 다른 스킬과의 경계

| 스킬 | 관계 |
|---|---|
| `my-plan` · `my-split` | 이 스킬이 **먼저**입니다. 1번 게이트를 통과한 뒤에 계획·분해로 넘어갑니다. 게이트를 통과했으면 그 결과(현재 동작·기대 동작·확정된 원인·제약)를 그대로 `my-plan` 입력으로 넘깁니다. |
| `my-interview` | 요청 자체가 모호할 때(무엇을 만들지 불명확)는 `my-interview`가 맞습니다. 이 스킬은 **무엇을 할지는 정해졌고 왜 그런지가 비어 있을 때** 씁니다. |
| `my-debug` | 원인 확정 절차(1번의 재현→관찰→추적→가설 검증)를 실제로 수행할 때 `my-debug`를 써도 됩니다. 단 **원인 판단은 여전히 사용자가 내립니다.** |
| `my-retro` | 5번에서 호출합니다. 회고 문서 작성은 `my-retro`가 담당하고, 이 스킬은 재료만 넘깁니다. |

**중복 발동 방지**: `my-retro`도 "작업 마무리하자" 같은 세션 종료 뉘앙스에 자동 발동합니다. 이 스킬이 5번에서 `my-retro`를 호출했다면 그것이 그 세션의 회고이고, 회고를 두 번 돌리지 않습니다. 반대로 사용자가 `my-retro`를 직접 불러 이미 회고가 끝났다면 이 스킬의 5번은 건너뛰고 **판단 로그만 제공**합니다.

## 0-2. 실행 환경 — Claude Code / Codex

절차는 양쪽이 같고, 쓰는 도구만 다릅니다. **도구가 없다고 절차를 건너뛰지 않습니다.**

| 필요한 것 | Claude Code | OpenAI Codex |
|---|---|---|
| 사용자에게 선택지 제시 | `AskUserQuestion` | 일반 메시지로 번호 붙인 선택지를 쓰고 답을 기다립니다 |
| 무거운 조사·검증 위임 | `Agent` tool (`repo-cartographer` 등) | 메인 루프가 직접 수행합니다 — 위임은 컨텍스트를 아끼기 위한 것이지 절차의 일부가 아닙니다 |
| 계획 모드 | plan 모드 | Codex의 계획 모드 / `PLAN.md` |
| 회고 문서 | `my-retro` 스킬 호출 | 동일 (`~/.codex/skills/my-retro`) |
| 이중 난이도 회고 | `eli5` 스킬이 있으면 사용 | 없으면 5-3의 마크다운 대체안을 씁니다 |

## 1. 착수 게이트 — 원인을 제대로 파악했는가

작업이 넘어왔을 때, 아래 4가지가 대화에 **이미** 있는지 확인합니다.

1. **현재 동작** — 지금 무엇이 어떻게 동작하는가
2. **기대 동작** — 어떻게 동작해야 하는가
3. **의심 원인** — 사용자가 생각하는 원인
4. **제약** — 건드리면 안 되는 것, 지켜야 할 패턴, 배포·호환성 조건

**빠진 것이 있으면 코드를 쓰기 전에 짧게 묻습니다.** 심문하지 마세요 — 빠진 항목만 한 번에 묶어 질문합니다. 이미 대화에 있는 항목을 다시 묻는 것은 게이트가 아니라 잡음입니다.

### 원인을 모를 때 — 원인 확정 절차

"의심 원인"이 없거나 추측 수준이면 바로 수정에 들어가지 말고 아래를 **먼저 제안하고 함께 수행**합니다.

1. **재현** — 문제를 확실히 재현하는 최소 조건을 찾습니다
2. **관찰** — 로그, 네트워크 응답, 상태 스냅샷 등 실제 데이터를 확인합니다
3. **추적** — 코드 흐름을 따라가며 기대와 실제가 갈라지는 지점을 특정합니다
4. **가설 검증** — "원인이 X라면 Y가 관찰돼야 한다"를 세우고 확인합니다

각 단계의 관찰 결과는 사용자에게 보여주고, **원인 판단은 사용자가 내리게 합니다.**

> ❌ "원인은 캐시 무효화 누락입니다. 고치겠습니다."
> ✅ "관찰된 사실: ① 새로고침하면 값이 맞습니다 ② 서버 응답에는 새 값이 들어 있습니다 ③ 화면 상태만 옛 값입니다. 이게 가리키는 유력한 원인은 캐시 무효화 누락입니다. 동의하시나요?"

**판단이 바뀐 순간은 회고의 핵심 재료입니다.** (예: "프론트 상태 문제인 줄 알았는데 서버 데이터 정합성 문제였다") 아래 판단 로그에 기록해 둡니다.

### 판단 로그

이 스킬이 발동한 순간부터 세션 내내 아래를 누적합니다. 파일로 쓰지 않고 대화 맥락에 유지하다가 5번에서 그대로 넘깁니다.

- 처음 가설 → 최종 확정된 원인, **그리고 바뀐 지점과 그 계기가 된 관찰**
- 제시한 선택지와 사용자가 고른 것, 버린 대안과 버린 이유
- 사용자가 판단한 것 vs AI에게 맡긴 것
- 관찰된 실제 데이터(로그·응답·상태) 중 판단 근거가 된 것

## 2. 설계 판단 — 선택지는 사용자에게

해결 방향이 하나로 자명하지 않으면 구현 전에 선택지를 제시합니다.

- **최소 수정 / 구조 개선 / 임시 대응** 중 어디에 해당하는지 표시
- 각 선택의 trade-off를 1~2줄로
- 변경 범위가 넓어 보이면 더 작은 문제로 분해하는 안을 먼저 제안

추천은 해도 되지만 **최종 선택은 사용자가 합니다.** 선택지 없이 하나의 방향으로 직행하는 것은 이 스킬을 어긴 것입니다.

## 3. 구현 중 — 판단 질문을 대신 던진다

코드를 쓰거나 검토할 때 아래에 스스로 답하고, **답이 불확실한 지점은 사용자에게 드러냅니다.**

- 이게 정말 원인을 고치는 건가, 증상만 가리는 건가?
- 기존 패턴과 맞는가? 과도한 변경은 없는가?
- 이 수정이 다른 경로를 깨뜨리지 않는가?
- 더 작은 변경으로 해결할 수 없는가?
- 실패한다면 어디서 실패할까?

사용자가 이해하지 못했을 법한 코드(트릭, 비직관적 로직)는 요청 없이도 짧게 설명합니다.

## 4. 검증 — 배포 판단은 사용자 몫

구현 후 확인 결과를 이 구조로 보고합니다.

```
✅ 원래 문제 : 해결 여부 + 근거(무엇을 보고 그렇게 판단했는지)
✅ 케이스    : 정상 / 경계 케이스 중 실제로 확인한 것
⚠️ 회귀 가능성: 의심 지점 — 확인하지 못한 경로를 포함
👉 배포 재료  : 롤백 가능 여부, 배포 후 관찰할 지표·로그
```

"배포해도 됩니다"라고 단정하지 말고 **판단 재료를 제공**합니다. 확인하지 못한 것을 확인한 것처럼 적지 않습니다.

## 5. 작업 마무리 — 회고

작업이 마무리되거나 사용자가 "회고", "정리해줘", "마무리하자"라고 말하면 아래를 수행합니다.

### 5-1. 회고 문서 — `my-retro`로 넘긴다

`my-retro` 스킬을 호출하고, **판단 로그를 재료로 함께 넘깁니다.** 형식·저장 경로·memory 승격은 전부 `my-retro`가 결정합니다. 이 스킬이 별도 포맷을 강요하지 않습니다.

넘길 재료:

- 문제와 최종 확인된 원인 — 처음 가설과 달랐다면 **판단이 바뀐 순간**을 반드시 포함
- 선택한 해결 방향과 근거, 검토했지만 버린 대안
- 사용자가 판단한 것 vs AI에게 맡긴 것
- 4번의 검증 결과와 남은 리스크

`my-retro`가 없는 환경이면 저장소 루트 `docs/retro/YYYY-MM-DD-<작업요약>.md`에 위 항목으로 직접 씁니다. `docs/retro/`가 없으면 **만들기 전에 묻습니다.**

### 5-2. 학습·인사이트 — `/my-memo`는 사용자가 실행

`my-memo`는 frontmatter에 `disable-model-invocation: true`가 있어 **모델이 호출할 수 없습니다.** Obsidian Vault에 직접 쓰는 스킬이라 의도적으로 잠가 둔 것입니다.

따라서 이 스킬은 호출을 시도하지 말고, 회고에서 **Vault에 남길 가치가 있는 인사이트**가 나왔을 때만 사용자에게 안내합니다.

> 남길 만한 인사이트가 있습니다: "<한 줄 요약>". Vault에 메모로 남기시려면 `/my-memo <내용>`을 실행하세요.

인사이트가 이 프로젝트 안에서만 유효한 것이면(코드 구조, 이번 버그의 특수 사정) 안내하지 않습니다 — 그건 5-1의 회고 문서와 memory에 남는 것으로 충분합니다. **다른 프로젝트·다른 상황에서도 다시 쓸 판단 기준**일 때만 안내합니다.

### 5-3. `eli5` 스킬이 있는 경우 — 이중 난이도 문서

`eli5` 스킬이 설치되어 있으면, 5-1의 회고와 **별개로** 같은 내용을 두 가지 난이도로 담은 설명 문서를 만들 수 있습니다. 회고 문서를 대체하지 않고 추가합니다. **만들기 전에 필요한지 사용자에게 묻습니다** — 모든 작업에 필요한 산출물이 아닙니다.

- **고등학생 버전** — 도메인 배경지식 없이 읽히는 설명
- **대학원생 버전** — 기술적 디테일, 정확한 용어, 코드·아키텍처 수준의 설명

형식은 일반 마크다운 텍스트가 아니라 **`eli5` 스킬이 추구하는 시각 중심 표현**을 따릅니다. `eli5` 스킬을 실제로 읽고 그 스킬이 제시하는 도구와 스타일을 적용하되, 최소한 다음을 적극 사용합니다.

- **다이어그램** — 문제의 구조, 원인→결과 흐름, 수정 전/후 비교를 그림으로
- **매트릭스·표** — 검토한 대안들의 trade-off 비교, 가설 vs 관찰 결과 대조
- **구체적인 예시** — 추상적 설명 대신 실제 입력·출력, 실제로 관찰된 로그나 응답
- **비유** — 특히 고등학생 버전에서, 도메인 개념을 일상 사물에 대응시키는 비유

글로 세 문단 쓸 내용이 그림 하나로 전달되면 그림을 택합니다. 텍스트는 그림과 예시를 잇는 접착제 역할로 최소화합니다.

저장 위치는 5-1과 같은 폴더에 `YYYY-MM-DD-<작업요약>-eli5.html`입니다. 상단에 `[고등학생 🎓 | 대학원생 🔬]` 전환 버튼을 두고 버전별 내용을 통째로 전환합니다. 사용자가 마크다운을 원하거나 `eli5`가 HTML을 쓰지 않는 환경이면 `<details>` 토글 + mermaid로 대체합니다.

두 버전은 **같은 사실**을 다루되 설명 층위와 시각화 방식만 다르게 합니다 — 쉬운 버전이라고 내용을 빼먹지 않습니다.

## 예외

- 순수 질문·설명 요청, 문서 작업, 1~2줄 변경에는 게이트와 회고를 강제하지 않습니다.
- 사용자가 **긴급 대응 중**이면 게이트를 건너뛰되, 마무리 시점에 회고만 제안합니다.
- 사용자가 **"그냥 해줘"**라고 하면 스스로 세운 가정을 명시한 뒤 진행합니다. 가정을 적지 않고 진행하는 것은 허용되지 않습니다.
- 같은 질문을 두 번 묻지 않습니다. 대화에 이미 답이 있으면 게이트는 통과한 것입니다.
