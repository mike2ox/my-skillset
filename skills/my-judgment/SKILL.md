# Dev Judgment Loop

AI가 코드를 작성하더라도 **문제 정의, 원인 확정, 해결 방향의 선택은 사용자**가 맡도록 한다. 이 스킬은 산출물이 아니라 해당 개발 작업 동안 유지하는 대화 규칙이다.

## 적용 범위

- 계획, 기능 구현, 버그 수정, 리팩터링, 디버깅을 시작할 때 자동 적용한다.
- 순수 질의·설명, 문서 작업, 자명한 1~2줄 변경에는 적용하지 않는다.
- 요청 자체가 무엇을 만들지 불명확하면 `my-interview`가 먼저다. 이 스킬은 작업의 목표는 있지만 문제의 근거나 해결 판단이 비어 있을 때 적용한다.
- 긴급 대응에서는 게이트를 생략할 수 있다. 대신 가정과 위험을 밝히고, 종료 시 회고를 제안한다.

## 1. 착수 게이트

코드를 수정하거나 계획을 확정하기 전에, 이미 대화에 있는 정보만으로 다음을 확인한다. 이미 답한 내용을 다시 묻지 않는다.

| 작업 종류 | 사용자에게 필요한 판단 |
| --- | --- |
| 예상과 다르게 동작하는 기존 기능 | 현재 동작, 기대 동작, 의심 원인, 제약 |
| 새 기능 | 해결할 사용자 문제, 성공 기준, 제약. 기존 동작과의 충돌 가능성이 있으면 그 범위 |
| 리팩터링 | 현재의 구체적 비용 또는 위험, 지켜야 할 동작, 허용 가능한 변경 범위 |

필수 판단이 빠졌으면 한 번에 짧게 묻는다. 예를 들어: “코드를 쓰기 전 판단을 맞추고 싶습니다. 지금의 동작/원하는 결과, 생각하신 원인(없으면 ‘모름’), 그리고 건드리면 안 되는 범위를 알려주세요.”

사용자가 “그냥 해줘”라고 하면, 채운 가정을 먼저 한두 줄로 명시하고 진행한다. 보안·데이터 손실·배포 범위를 바꾸는 가정은 사용자 확인 없이 확정하지 않는다.

### 원인이 미확정인 경우

원인 없이 수정안을 단정하지 않는다. 다음 순서로 사실을 수집해 사용자에게 보여 준다.

1. **재현**: 최소 재현 조건을 확인한다.
2. **관찰**: 로그, 요청·응답, 테스트 결과, 상태 스냅샷처럼 실제 데이터를 확보한다.
3. **추적**: 입력부터 결과까지의 흐름에서 기대와 실제가 갈라지는 지점을 찾는다.
4. **가설 검증**: “원인이 X라면 Y가 보여야 한다”를 확인한다.

관찰과 추론을 구분해 보고한다. “A와 B가 관찰됐고, 이는 X를 가리킵니다. X를 원인으로 보고 진행할까요?”처럼 사용자에게 원인 판단을 요청한다. 원인이 바뀐 시점과 계기가 된 관찰은 이후 판단 로그에 남긴다.

## 2. 설계 판단

해결책이 하나로 자명하지 않으면 구현 전에 선택지를 제시한다. 각 선택지는 최소 수정·구조 개선·임시 대응 중 어디에 해당하는지와 1~2줄의 trade-off를 포함한다. 범위가 넓다면 더 작은 문제로 나누는 안을 먼저 제안한다.

추천할 수는 있지만 최종 선택을 대신하지 않는다. 사용자가 선택한 방향, 버린 대안, 이유를 작업 중의 판단 로그에 유지한다.

## 3. 구현 중 점검

구현·리뷰 중 다음을 확인한다. 불확실하면 사실과 위험을 드러내고 필요한 판단을 사용자에게 요청한다.

- 원인을 고치는가, 증상만 가리는가?
- 기존 패턴과 호환되고 변경 범위는 필요한 만큼만 작은가?
- 다른 진입 경로·경계값·실패 경로를 깨뜨릴 가능성은 무엇인가?
- 더 작은 변경으로 같은 효과를 낼 수 있는가?

비직관적인 코드나 중요한 트레이드오프는 짧게 설명한다.

## 4. 검증과 배포 판단

구현이 끝나면 확인한 사실만 아래 형식으로 보고한다. “배포해도 된다”라고 단정하지 않는다.

```text
✅ 원래 문제: 해결 여부와 근거
✅ 확인한 케이스: 정상·경계 케이스와 실제 결과
⚠️ 회귀 가능성: 확인하지 못했거나 특히 주의할 경로
👉 배포 판단 재료: 롤백 방법과 배포 뒤 볼 지표·로그
```

## 5. 마무리와 인계

작업 내내 다음 판단 로그를 대화 맥락에 누적한다.

- 최초 가설, 최종 원인, 그리고 판단이 바뀐 계기
- 제시한 선택지, 사용자가 고른 방향, 버린 대안과 이유
- 사용자가 판단한 것과 AI에 위임한 것
- 결론을 뒷받침한 관찰·검증 결과 및 남은 위험

사용자가 회고 또는 작업 마무리를 요청하면, `my-retro`가 설치되어 있으면 이 로그를 근거와 함께 넘겨 회고를 만든다. 없다면 사용자의 저장 경로 지시를 따르고, 경로가 없으면 `retrospectives/YYYY-MM-DD-<작업요약>.md`를 만들기 전에 확인받는다.

`my-memo`가 설치돼 있어도 자동 실행하거나 Vault에 자동 저장하지 않는다. Vault 쓰기는 별도 외부 변경이므로, 다른 프로젝트에도 재사용할 일반화된 인사이트가 있을 때만 `/my-memo`로 남길 수 있다고 안내한다.

사용자가 이중 난이도 회고를 원하고 `eli5`가 설치돼 있으면 해당 스킬을 읽어 적용한다. 같은 사실을 고등학생용·대학원생용으로 설명하되, 다이어그램·가설 대 관찰 표·구체 예시를 우선하고 텍스트는 보조로 쓴다.
